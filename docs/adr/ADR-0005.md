# ADR-0005 · 发布制品与 release.json（目标态，本期不实施）

- 状态：**Proposed（目标设计，尚未实施）**
- 日期：2026-10-14
- 关联：ARCHITECTURE §12 P5、§15.8；REQUIREMENTS 附录 A（B8）

> 本 ADR 记录已评审通过的**目标方向**，便于后续专项启动时直接细化。P0–P3 **不实现** release.json，也不做单 artifact 双发；当前仍是「GitHub Pages 与 Cloudflare 各自按源码构建」。

## 上下文（Context）

主站（GitHub Pages，子路径 `/hardware-handbook/`）与国内镜像（Cloudflare Pages，根路径 `/`）目前各自在自己的流水线里跑一次构建，产物独立、构建时间不同；下游（镜像、离线分发、未来门户）也缺少一个可机读的「当前发布了哪个内容版本」的声明。

## 目标决策（Decision）

- 在线构建产物旁输出 `release.json`，字段至少包含：
  - `appId`、`contentRevision`（取自 manifest，见 [ADR-0002](ADR-0002.md)）；
  - `builtAt`（ISO 时间）、`gitSha`、`base`；
  - `docCount`、`indexUrl`、`assetsManifest`（关键资源及校验值）。
- 以**同一份构建 artifact** 双发到 Pages 与 Cloudflare（backlog B8），避免两条流水线产物漂移；base 差异在产物内通过相对路径或部署期配置处理，而非重复构建。
- 离线单文件 HTML 与在线 release 共享同一 `contentRevision`，便于核对「离线包对应哪一版在线内容」。

## 待实施时必须确定的开放问题

1. base 子路径与根路径能否共用一个 artifact（评估 VitePress `base` 对绝对资源 URL 的影响）；若不能，是构建两份还是运行时改写。
2. release.json 由哪一步生成、签名/校验到什么程度。
3. 旧版本回滚时 release.json 的历史保留策略。

## 后果（Consequences）

- 实施前需将本 ADR 从 Proposed 升级为 Accepted，并补一项 CI 校验（release.json 与 manifest 对账）。
- 在落地前，`pnpm verify` 不包含 release.json 校验；部署仍沿用现有两套 workflow。
