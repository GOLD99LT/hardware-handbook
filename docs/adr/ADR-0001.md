# ADR-0001 · 采用 pnpm Monorepo 组织多专项

- 状态：Accepted（已落地，P1）
- 日期：2026-10-14
- 关联：ARCHITECTURE §2、§12 P1；[ADR-0002](ADR-0002.md)、[ADR-0003](ADR-0003.md)、[ADR-0004](ADR-0004.md)

## 上下文（Context）

硬件手册最初是单目录 VitePress 站（`docs/` 既是内容又是站点工程）。路线图规划了更多专项（嵌入式软件开发手册、软硬件协同、门户），若每个专项各建一套，会重复维护：

- 通用 Markdown 规则（五类容器、KaTeX、CJK 强调、折叠题、ECharts、图片 figure、面包屑）；
- 主题、品牌、学习功能（进度/收藏/笔记/导入导出）；
- 离线单文件构建与质检脚本（Python）；
- 内容清单（manifest）、部署与 CI。

需要在「能多 app 共享」与「内容仍是唯一事实源、离线零依赖」之间取舍。

## 决策（Decision）

采用 **pnpm workspace Monorepo**，顶层布局：

```
apps/*        # 各专项（handbook；未来 embedded…）
packages/*    # @hw/shared-config、@hw/theme、@hw/content-core、@hw/learning、@hw/components、@hw/svg-kit
templates/*   # site-template（新专项脚手架）
packages/tooling/   # Python 离线构建/质检/vendor（非 npm 包，保持零第三方依赖）
```

- 包管理器固定 **pnpm**（根 `package.json` 的 `packageManager: pnpm@12.11.2`），通过 **corepack** 启用，不做全局降级、不换 npm/yarn；启用失败必须停下反馈。
- 内部包间引用用 `workspace:*`；共享包以源码 TS 直接消费（`exports` 指向 `./src/index.ts`，无预构建），`vite.ssr.noExternal=[/@hw\//]`。
- 每个 app 自带薄 `config.mts`（调 `defineHwConfig`）与 `content.config.ts`（part registry、站点元数据、装配学习仓储）。
- Python 工具链**不**重写为 Node、**不**做成 pnpm 包（见 [ADR-0004](ADR-0004.md)）。
- 模板 `templates/site-template` 为最小可构建 app，复制后改 appId/title/base 即得新专项。

## 备选方案（Alternatives）

- 继续多仓库/单站复制：每个专项重复维护通用规则与工具，易漂移，否决。
- npm workspaces：无法满足对包提升、构建脚本（`allowBuilds`）的精细化控制；团队统一选 pnpm，否决。
- 用 Turborepo/Nx 等编排层：当前只有 2 个可构建 app、构建不重，引入过度工程，列为 backlog。

## 后果（Consequences）

- 一次 `pnpm install` 装好全部 workspace，`pnpm --filter @hw/handbook <script>` 按 app 执行；`pnpm-lock.yaml` 唯一。
- pnpm 12 的构建脚本许可改用 `pnpm-workspace.yaml` 的 `allowBuilds`（旧 `onlyBuiltDependencies` 已移除，见 PLAYBOOK 故障节）。
- 内容与站点工程解耦，新专项可直接复用全套规则与学习功能；代价是目录与构建命令有一次学习成本。
- 任何对共享包签名/构建方式的变更，必须同步改所有 app 与模板并跑 `pnpm verify`。
